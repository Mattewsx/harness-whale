# AI Passport BLE 协议 2.3

协议 2.3 在 2.2 之上增加可协商的大帧，已有消息体不变，与 2.2 桥接器、固件双向兼容。v1.4.0 整合版还新增可选时钟消息 `0x53`，旧固件忽略该类型。当前链路以 Python [`whale_v2.py`](../harness/bridge/whale_v2.py) 和 C [`whale_wire.c`](../device-firmware/main/whale_wire.c) 为准。`harness_ble_protocol.py` 中的 v1 帧和余额字段为旧版兼容实现，不代表当前传输格式。

| 项目 | UUID |
| --- | --- |
| Service | `13b50200-663a-48c5-a224-37c1c2569080` |
| Write | `13b50201-663a-48c5-a224-37c1c2569080` |
| Notify | `13b50202-663a-48c5-a224-37c1c2569080` |

整数为小端。碎片头采用 `<BBHBBH`：帧版本、消息类型、16 位序号、碎片索引、碎片总数、消息体总长度。帧版本 2 为传统帧：每个 ATT 帧最多 20 字节，头部 8 字节、数据最多 12 字节。帧版本 3 为 2.3 大帧：每帧最多为协商的帧长 F（21–244 字节），数据最多 F−8 字节，碎片总数按 F−8 计算。控制与批量消息独立重组；一条消息的所有碎片必须使用同一帧版本和帧长；越界、乱序、超时及过期序号被拒绝。

## 握手与大帧协商（2.3）

桥接器发送的 `0x01` 仍是 2.2 格式 `<BBIHH`：主版本 2、次版本 2、能力位、可接收帧长、可发送帧长，因此旧固件照常接受。设备回复 `0x02`（`<BBIHHB`，末字节为状态）。

| 位 | 含义 |
| --- | --- |
| 0–5 | 2.2 必需能力，必须全部置位 |
| 6–11 | 2.2 / v1.3 已有可选能力（含运行细节 7、回复阅读 8、语音 9、待处理优先 10、全局摘要与提醒 11） |
| 12 | 2.3 大帧（本版新增） |

1. 桥接器按 ATT MTU 取 `min(244, MTU−3)`；大于 20 时在 hello 中置位 12，并把可收、可发帧长都填为该值，否则保持 20 且不置位。
2. 2.3 固件看到位 12 时回复次版本 3；授予帧长 `F = min(桥接器可收, 桥接器可发, 244, 设备侧 MTU−3)`。仅当 F > 20 时回复置位 12，并在可收、可发帧长中都填 F；否则不置位且填 20。hello 被拒绝时（状态非 0）一律不授予。
3. `0x02` 回复本身仍用帧版本 2。此后双方发送的新消息都改用帧版本 3、帧长 F；接收端仍接受帧版本 2，便于切换期间已开始的消息完成。
4. 桥接器只在回复为次版本 3、置位 12、两个帧长相等且不超过自己所报值时启用大帧，其余情况（包括 v1.3.1 及更早固件的 `2.2 / 20 / 20` 回复）保持 20 字节帧。
5. 断开连接后双方回到帧版本 2；每次连接都重新协商。

固件只为大于 20 字节的写入使用 8 个 244 字节的环形槽（约 2 KB），按顺序处理并释放，事件队列中的传统帧格式不变。槽位占满时写入返回资源不足，与原先事件队列满时的处理相同。桥接器通过 `/whale` 的 `BLE frame` 行和本机遥测的 `frame` 字段显示当前帧长。

| 消息 | 用途 |
| --- | --- |
| `0x01/0x02` | 协议、能力与帧长协商 |
| `0x10` | 请求会话列表窗口 |
| `0x11/0x12/0x13` | 快照开始、条目、完成和校验 |
| `0x14` | 会话状态更新 |
| `0x16/0x17` | 完整标题请求和返回 |
| `0x18` | 单次运行的显示细节 |
| `0x19` | 最近回复修订及摘要 |
| `0x1A/0x1B` | 指定回复分段请求及返回 |
| `0x20/0x21` | 问题与选项 |
| `0x22/0x23/0x24/0x25` | 单选提交、结果、选项读取与结果查询 |
| `0x30/0x31/0x32` | 心跳、回执与错误 |
| `0x53` | 墙钟（v1.4.0 起，可选，批量通道）：`<QqH>` epoch、Unix 秒（int64）、电脑本地时区相对 UTC 的分钟数（int16）。桥接器在首个快照之后发送，连接期间每 30 分钟重发；固件只在快照就绪且 epoch 一致时接受，时间需在 2020–2099 年、时区在 ±14 小时内。旧固件忽略未知类型 |

回复请求体是 `<QIII`：epoch、会话、修订、分段索引；响应是 `<QIIIIH` 加 UTF-8 文本，另带总分段数和字节长度。分段是传输细节，不是多条历史回答，UI 不显示分段页码。仅当前请求的会话、修订与分段可进入阅读窗口。

状态包含离线、待命、思考、执行、等待、完成、错误、停止、问题。进度只在有真实 Todo 总数时显示。余额协议兼容字段不会在 R10.1 UI 展示。字体覆盖 GB2312 一级汉字和固定界面文本，标题、选项和正文经过清洗/安全 UTF-8 截断；不支持字符可能显示替代符号。

端到端兼容性以 [Python→C 回放](../tests/firmware-replay/RUN.txt) 验证，不用文档代替源代码中的消息长度、边界及能力检查。

## 语音派新任务（能力位 16）

桥接器在 hello 中置位 16（65536）；固件只在同时支持语音（位 9）时回显。双方都置位后，主页底栏“说任务”可录一段新任务。位 15 留给富问题（审批、多选）。

| 消息 | 方向 | 内容 |
| --- | --- | --- |
| `0x48` | 设备→桥接器（控制） | `<QI16s>`：epoch、当前选中的会话（0 表示无，仅作为选文件夹的参考）、录音 nonce。与 `0x40` 同形，但目标是新会话 |
| `0x49` | 桥接器→设备（控制） | 24 字节身份（epoch + nonce）加最多 48 字节 UTF-8 文件夹名，在 `0x41` 就绪之前发送 |

录音、上传、识别、发送和查询沿用 `0x41`–`0x47`，身份相同。状态码新增 14：电脑上没有可用文件夹，只在新任务中有效。桥接器收到确认后调用插件 `/create`（查询用 `/create-query`），插件用宿主默认模型和 preset 新建顶层会话、挂到对应工作区，再把识别文字作为首条消息。插件按 nonce 记账，重复确认或重试不会开第二个会话；插件重启后查询只回答“不确定”，不会补开。文件夹必须是某个可见主会话正在使用的目录。旧固件不回显位 16、旧桥接器不发位 16，两种情况都不会出现 `0x48`。

## v0.15.0 本地 Demo 的未读会话

双方在 HELLO 中协商能力位 13（8192）。启用时，行标志 32 表示尚未查看的问题，64 表示已完成但没有最终回复的本轮尚未查看。沿用 8 和 16 表示未读最终回复和错误。全局摘要 `0x50` 的未读数按具有任一标志的会话去重，覆盖所有列表窗口。

设备在相应内容绘制到亮屏后发 `0x4a`，消息为小端 `<QIIB>`（epoch、会话、修订、类型）。类型 1 绑定回复修订，2 绑定错误运行，3 绑定题目 ID，4 和 5 分别绑定无正文完成和需电脑处理问题的运行。桥接器验证身份并维护已读记录。查看题目和提交答案是两个操作，提交仍使用 `0x22`。旧设备协商时不启用新增行标志。

从主页打开列表时，优先级依次为未看的待回答事项、未读错误、未读回复或无正文完成、看过但尚待回答的事项、运行或普通等待，最后为其他会话。同级保留原顺序。协商能力位 14（16384）后，`0x10` 末字节 2 请求重新排序，0 沿用当前顺序翻页。

能力位 14 也启用跨窗口回复缓存。`0x1c` 为批量通道消息，小端 `<QQII>`（epoch、失效序号、会话、旧回复修订）。更新、删除或归档使旧修订失效。桥接器保留最近 32 条失效记录，重连后重放；设备忽略重复序号，发现缺口时清空正文缓存。普通翻页只更新列表及回复元数据。旧桥接器仍按窗口回收缓存。
